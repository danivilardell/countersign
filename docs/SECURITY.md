# Prototype limitations

Countersign is a prototype of the I-HITL design, not an audited service. See the paper for the design and its guarantees.

- **Android verification:** the service checks the attestation chain's signatures, validity periods, CA constraints and trust root, but not certificate revocation or full X.509 path validation. Google's root certificates must be refreshed by hand.
- **iPhone:** App Attest is checked at enrollment only. It does not attest that the confirmation key lives in the Secure Enclave or requires biometrics; those properties rely on the genuine app and OS.
- **Ledger:** the service verifies a chain from Ledger's published root of trust (`attestation_roots/ledger_root_of_trust.txt`, the key printed in Ledger's device guides) to the device key (issuer certificate) to the endorsement key (device signature over `0xFF || key`), the pinned app code hash, and every approval signature over `message || code_hash`. The chain is captured by the user's own bridge from the device dashboard, so provisioning is remote and needs no secret; a user cannot forge it because only a genuine device's key can sign an endorsement key. Ledger OS never exports endorsement keys, which is what makes delegation to an agent impossible. Alternatively a deployment can accept Owner certificates (`0xFE || key`) under `COUNTERSIGN_LEDGER_OWNER_PUBLIC_KEYS`; that trust is only as good as the Owner, and an Owner who is also the device's user can certify a software key. Ledger's HSM endorsement endpoint is no longer reachable, and the root key is checked for the current batch only: a device from a batch with a different root would be rejected until its key is added. Display and input trust rest on Ledger OS app isolation; there is no per-approval device-integrity evidence, as on iOS. A message is limited to 255 bytes.
- **Proof of approval:** `GET /v1/admin/approvals/{ref}/proof` returns the signed message, signature, public key and, for Android, the attestation chain, for a Ledger the code hash, the slot certificate and the device chain. It omits the Play Integrity verdict, which can only be decoded with the operator's Google Cloud credentials, so independent verification would need access to that service account. The iPhone proof does not include the attestation.
- **Android emulator:** the simulation build and backend skip attestation and Play Integrity. A simulated fingerprint is a test input.
- **Ledger emulator:** Speculos signs with published default keys; the simulation backend pins them, so the verification code runs but nothing is proven about a real device.
- **Display:** the Android approval screen's overlay defenses are best-effort, and the screen is not a protected display.
- **Service:** The backend is a minimal implementation using shared bearer tokens (the device token is compiled into the Android app and read from the environment by the Ledger bridge), a single-process SQLite store, and no rate limiting, tenant isolation or device revocation.
- **Testing:** the automated tests use Google's example certificates and synthetic data. Real-device flows must be run by hand.
